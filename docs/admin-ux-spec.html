Admin Dashboard
UX Requirements

Specification for four internal pages used to operate Scholar Seek's paper crawler and manage staff accounts. Written for a designer producing wireframes and visual design — flows and content are fixed, layout and visual treatment are open.

AudienceRoot admin + admin-role staff only. Not end-user facing. SurfaceWeb app, existing light/dark theme toggle already in place. Existing kitButton, Card, Input, Badge, Checkbox, Separator, Sonner toasts.
00

Scope & shell

What every admin page shares, before getting into any one of them.

Context

Scholar Seek is an academic paper search engine. Its catalog is populated by a background crawler that pulls from three sources — arXiv, Semantic Scholar, and DOAJ — on schedules an admin defines. This spec covers the four pages an admin uses to run that system: an overview, the schedule editor, a history/audit log, and staff account management.

Two roles, one distinction that matters

  • Root admin — exactly one, seeded at install. Cannot be demoted, banned, or deleted by anyone, including itself. The UI needs to make this visible (disabled controls with a reason), not just let the action fail.
  • Admin — created by an existing admin (there is no public sign-up). Full access to all four pages, with the one exception above.

Shell & navigation

All four pages sit behind one persistent admin shell: a nav (rail or top bar — designer's call) with four destinations, the current page indicated, and a sign-out control. Anyone without an admin role sees none of this — the shell itself is the access boundary.

Shell — content regions
  • Persistent nav: Overview · Schedules · History · Users
  • Signed-in-as indicator (email + role chip)
  • Page content region — this is what pages 01–04 below describe
01

Overview

The landing page. One question it has to answer in five seconds: is anything broken right now?

Primary tasks

  • Gauge catalog size and growth at a glance
  • Spot a stalled schedule or a failing crawl without visiting History
  • Jump straight to whatever needs attention

Content regions

Layout — top to bottom
  • Attention strip — only appears when something needs looking at: a schedule whose last run failed, or a run currently past its estimated duration. Empty/hidden when everything is healthy. This sits above the fold, not buried in a tab.
  • Stat tiles — total papers, added in last 24h, added in last 7d, embedding coverage %, active schedule count, schedules currently running.
  • Source breakdown — papers by source (arXiv / Semantic Scholar / DOAJ), count and share of total.
  • Recent activity — last ~10 crawl runs across all schedules, each row linking into the full History page.

States

  • Loading — tiles and rows show placeholder shapes matching their final size, not a spinner over blank space.
  • Fresh install — 0 papers, 0 schedules run yet. Needs a real empty state with a next action ("Create your first schedule"), not a wall of zeroes.
  • 0% embedding coverage — expected right after a fresh crawl, before the ML backfill catches up. Should read as "in progress," not "broken."
02

Schedules

Where crawls get defined, run, and watched. The most involved page in the set — three flows, described in order below.

Primary tasks

  • See every schedule and its health at a glance
  • Create a new schedule, or edit an existing one
  • Trigger a manual run, watch it progress, cancel it if needed

List view

Per-schedule row/card contents
  • Name, and cadence in both forms — human-readable ("Daily at 03:25") and the raw pattern (25 3 * * *) for anyone who wants to verify it
  • Enabled / disabled state
  • Source badges — a schedule can mix sources across its targets now (see below), so this row shows one badge per distinct source in use, not a single value
  • Target count
  • Last run — status and relative time ("completed 3h ago", "failed 1d ago")
  • Actions: Edit, Run now, Enable/Disable, Delete

Filter by enabled state and by source once the list grows past a handful — not required for a first pass with only a few schedules.

Empty state: no schedules yet, with a clear "Create a schedule" call to action — this is likely the very first thing a fresh install's admin sees.

Create / edit flow

  1. Name and cadence A name field, plus a cadence builder — not a raw cron input as the primary control. Offer "Daily at [time]" and "Weekly on [day] at [time]" as guided options, with "Custom" as an escape hatch to type cron directly for power users. Always show the resulting pattern in both forms underneath, so the guided option and the escape hatch stay visibly in sync.
  2. Targets — one or more, each independently sourced A repeatable list. Each row is its own small form, and the source choice comes first because it changes what the rest of the row asks for:
    SourceQueryCategories
    arXivNot shown — not applicable to this sourceMulti-select, arXiv subject list
    Semantic ScholarShown, required — inline error if left blankMulti-select, field-of-study list
    DOAJNot shownMulti-select, DOAJ subject list
    Every row also has a label (free text, the admin's own reference — e.g. "S2 — machine learning"), a max-records field with a visible ceiling, and a remove action (disabled on the last remaining row). "Add target" sits below the list. A schedule with three targets — one per source — is exactly as valid as one with a single target; the form shouldn't privilege either shape.
  3. Review before saving A short computed summary — target count, sources involved, combined max records — shown just before the save action. This is the same kind of number the run-now flow shows before executing; showing it at creation time too means nothing about scale is a surprise later.

Run-now flow

  1. TriggerAdmin clicks "Run now" on a schedule.
  2. Estimate System shows target count, total requests, and an estimated duration, computed from what's actually configured — not a placeholder. If any target uses Semantic Scholar without an API key configured, show a warning: the shared public rate pool can make the real run slower than the estimate.
  3. Confirm — two tiers Below a safe-cost threshold: one "Confirm run" action. Above it: extra friction — the admin must type a confirmation phrase before "Run anyway" becomes clickable. The root admin bypasses this second tier, but the UI should say so visibly (e.g. a small "root admin — override not required" note) rather than silently skip a step a designer might otherwise assume always appears.
  4. Progress Live element: targets completed out of total, elapsed vs. estimated time. The moment any target fails, a distinct failed-count indicator appears alongside the completed count — "completed" must never visually read as "all succeeded" when it isn't. This was a real bug in the first version of this page; the design should make it structurally hard to repeat.
  5. Cancel Available while running. Removes targets that haven't started yet; whatever's already running finishes on its own and keeps its real outcome.

Why the two-tier confirm exists

A schedule can be small (one target, a few hundred records) or effectively a full backfill (many targets, tens of thousands of records each). The threshold exists so a small daily schedule stays a one-click action while a heavy one gets a genuine "are you sure" — the design should make that difference in weight obvious, not just a longer button label.

03

Crawl history

The audit log. Used for debugging — what ran, when, did it work.

Primary tasks

  • Scan recent activity across every schedule in one place
  • Filter down to a specific source, status, or date range
  • Open one run's detail to see exactly what happened and why
  • Jump back to the schedule that produced a given run

Content

Filter bar
  • Source (all / arXiv / Semantic Scholar / DOAJ)
  • Status (running / completed / failed)
  • Date range
Table columns
  • Started (sortable)
  • Source
  • Status — as a chip, see Shared Patterns, not plain text
  • Papers found / inserted / skipped
  • Duration (sortable)
  • Parent schedule — linked back to that schedule's edit page

Row detail (expand-in-place or side panel): full error list when failed, and the exact options used for that run — query, categories, max records, since-date — so a failure is reproducible without guessing.

States & edge cases

  • A running row needs a visibly different treatment from a finished one — not just a different word in the same chip position.
  • Long error messages truncate with an expand control, never silently overflow the row.
  • Paginate — this table will outgrow a single page quickly once schedules run daily for months.
04

User management

Access control for staff. There is no public sign-up — this page is the only way a new account gets created.

Primary tasks

  • See everyone with access and their current role/status
  • Create a new staff account
  • Change a role, ban, or remove a user
  • Inspect and revoke a user's active sessions

Content

Table columns
  • Email, name
  • Role — chip (root admin / admin / user)
  • Status — active / banned
  • Created date
  • Actions

The root admin's row is a special case

Its role/ban/remove actions are visibly disabled, with a short reason on hover or as inline caption ("Root admin cannot be modified") — not present-and-clickable-but-silently-rejected. The backend already enforces this; the UI's job is to make the constraint legible before someone tries.

Create account

Since this is the only path to a new account, its entry point needs to read as a primary action on the page — not a small icon tucked in a corner.

Sessions

Per-user, on demand (e.g. from a row action): list of that account's active sessions. Each has an individual "Revoke," plus a "Revoke all" for the whole account — useful the moment an admin suspects a compromised login, independent of banning the account outright.

Confirmation weight

Ban and remove are high-impact. Both need an explicit confirm step — a modal with the consequence stated in plain words, not a bare click-and-done. This doesn't need the typed-phrase tier from the Schedules run-now flow; a standard confirm dialog is enough here.

05

Shared patterns

Cross-cutting rules the designer should treat as a small system spanning all four pages, so an admin doesn't have to relearn conventions per screen.

Confirmation tiers

Three weights, used consistently:

  • Standard confirm — modal, one clear action (ban, remove, delete schedule)
  • Escalated confirm — typed phrase required (run-now above the cost threshold, only)
  • No confirm — reversible, low-cost toggles (enable/disable a schedule)

Toasts

Every mutation gets one — create, update, delete, run, cancel, ban, revoke. Success and failure both surface here, not just failure.

Status chips

One visual language, reused everywhere a state appears: schedule enabled/disabled, run running/completed/failed/cancelled, user active/banned, crawl status. Same shape and color meaning on every page.

Empty states

Every list gets one, and every one of them includes a next action — never just an illustration and "no data."

Loading

Skeleton placeholders shaped like the content they'll become (a tile-shaped block for a stat tile, a row-shaped block for a table row) — not a centered spinner over empty space.
